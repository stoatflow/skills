## `stoatflow`

Core StoatFlow configuration for stream processing

| Key | Type | Default | Description |
|---|---|---|---|
| `stoatflow.application-id` | string |  | Unique identifier for this application. Used for consumer group and transactional ID. |
| `stoatflow.bootstrap-servers` | string | `localhost:9092` | Kafka bootstrap servers (comma-separated list). |
| `stoatflow.lanes.count` | integer | `max(2, CPU cores / 4)` | Number of key-affinity lanes per sub-topology; each lane processes a subset of the keys, in order. Default: max(2, CPU cores / 4) — 2 lanes up to 11 cores, 3 at 12, 4 at 16 — read once at startup; a per-sub-topology withNumberOfLanes wins. More lanes cost CPU per record; two lanes can cap a CPU-bound stateful sub-topology, so raise the count when consumer lag grows while the CPU is idle. For blocking I/O in user code, raise it and set thread-type: VIRTUAL. Left unset under the TopologyTestDriver (StoatFlowTestDriver), the timer lane-affinity checks judge over a fixed reference count of 16 lanes, so a test does not depend on the build machine's cores. |
| `stoatflow.lanes.queue-capacity` | integer | `300` | Capacity of each lane's queue. Controls backpressure - when full, the dispatcher blocks until space is available. |
| `stoatflow.lanes.thread-type` | enum | `PLATFORM` | Thread type of the record lanes, for every sub-topology. PLATFORM (default): one OS thread per lane, the cheapest at the default lane count. VIRTUAL: Project Loom virtual threads, which pay off with many lanes, e.g. for blocking I/O in user code (raise lanes.count too). Punctuation lanes are always virtual threads. A sub-topology with more PLATFORM lanes than CPU cores logs a WARN at startup. One of: PLATFORM, VIRTUAL. |
| `stoatflow.commit-barrier.interval-ms` | integer | `500` | Seed interval between commit barriers in milliseconds. Used as the initial interval before post-commit scheduling adjusts it. |
| `stoatflow.commit-barrier.timeout-ms` | integer | `60000` | Timeout for commit barrier completion in milliseconds. Bounds every .join()/.get() on the commit critical path via BoundedAwait. Also cascades to Kafka producer transaction.timeout.ms, max.block.ms, and delivery.timeout.ms via forced overrides. Must be greater than interval-ms. |
| `stoatflow.commit-barrier.dedicated-commit-thread` | boolean | `true` | Whether to use a dedicated platform thread for commit barrier execution. When enabled, commits run on a separate thread instead of inline on the last lane thread, preventing lane stalls during Kafka transaction commit and RocksDB epoch flush. |
| `stoatflow.commit-barrier.interval-factor` | number | `1.5` | Barrier interval as a multiple of estimated commit duration. 1.0 = back-to-back commits (interval equals commit time). 1.5 = interval is 1.5x commit time. |
| `stoatflow.commit-barrier.min-interval-ms` | integer | `150` | Minimum barrier-to-barrier interval in milliseconds (wall-clock time from barrier N creation to N+1 creation). |
| `stoatflow.commit-barrier.max-interval-ms` | integer | `5000` | Maximum barrier-to-barrier interval in milliseconds. |
| `stoatflow.commit-barrier.idle-interval-ms` | integer | `30000` | Idle-throttle interval in milliseconds (ADR-134). When a warm-idle EOS app produces 5+ consecutive empty epochs, the barrier scheduler parks this long between empty commits instead of the min-interval-ms floor (~200x less idle transaction churn). The cadence snaps back with no added latency as soon as real work reappears. Effective value is clamped to min(idle-interval-ms, timeout-ms/2) at engine start (WARN on clamp). Engages for a warm-idle exactly-once app, and — since RS-18 made reclamation idle-safe — for an at-least-once app that still has a versioned store left to sweep. Set to 0 to disable the throttle (restores pre-ADR-134 behavior). |
| `stoatflow.commit-barrier.commit-duration-ema-alpha` | number | `0.15` | Commit duration EMA smoothing factor. Higher values make the estimate more responsive to recent samples, lower values produce smoother estimates. Controls how quickly the barrier scheduler adapts to changes in commit duration. |
| `stoatflow.commit-barrier.max-epoch-records` | integer |  | Hard cap on records dispatched per epoch. When set, limits the S1 feedback controller output to prevent unbounded epoch growth. Smaller values reduce producer flush time at commit but increase commit frequency. Unset = no hard limit. |
| `stoatflow.commit-barrier.initial-max-epoch-records` | integer | `4096` | Initial cap on records dispatched per epoch before the S1 feedback controller has learned the topology's memory profile. Only affects the first epoch(s) after startup — subsequent epochs are governed by S1 (ADR-091/ADR-107). Set to -1 to disable. |
| `stoatflow.commit-barrier.memory-cap-ema-alpha` | number | `0.1` | EMA smoothing factor for the memory-based epoch size cap. Controls how quickly the feedback controller adapts to changes in per-record state size. Lower values smooth more aggressively. |
| `stoatflow.commit-barrier.epoch-records-ema-alpha-grow` | number | `0.3` | EMA smoothing factor for the epoch records safety cap on the GROW path (S1 binding-aware update, ADR-107). Used when a binding signal fires (RECORD_COUNT, CACHE_PRESSURE, a dispatcher stall behind either, or soft binding) or when the natural rate is rising; an epoch bounded by memory pressure is never one. Higher values react faster to growth. |
| `stoatflow.commit-barrier.epoch-records-ema-alpha-decay` | number | `0.05` | EMA smoothing factor for the epoch records safety cap on the DECAY path (S1 binding-aware update, ADR-107). Used only when no binding signal fired and the natural rate is declining. Lower values resist transient drops more strongly. |
| `stoatflow.commit-barrier.capped-growth-factor` | number | `1.3` | Multiplicative growth floor on smoothedEpochRecords whenever the cap was binding this epoch (ADR-107). Guarantees monotonic growth out of a collapsed equilibrium independently of the alpha-driven EMA update. Set to 1.0 to disable. |
| `stoatflow.commit-barrier.soft-binding-ratio` | number | `0.9` | Soft-binding threshold for the S1 feedback controller (ADR-107). On TIME-triggered epochs, the cap is treated as effectively binding when actual/cap >= ratio, even though the dispatcher did not literally hit the RECORD_COUNT threshold. Lower values widen what counts as binding (more eager grow). Set > 1.0 to disable soft binding entirely. |
| `stoatflow.commit-barrier.process-latency-ema-alpha` | number | `0.1` | EMA smoothing factor for per-record process latency (rate-based cap). Lower than epoch-records-ema-alpha-grow to resist outliers from filtered records. |
| `stoatflow.commit-barrier.duration-ema-alpha` | number | `0.3` | EMA smoothing factor for barrier duration overrun ratio. Controls how quickly the duration-based throttle reacts to barrier intervals exceeding max-interval-ms. |
| `stoatflow.commit-barrier.min-epoch-records-factor` | number | `0.5` | Minimum epoch records factor for the S1 safety cap floor. Prevents maxEpochRecords from dropping below a fraction of the recent epoch average (smoothedEpochRecords × factor). Stabilizes epoch sizes for heterogeneous workloads. Set to 0.0 to disable. |
| `stoatflow.commit-barrier.max-engine-restarts` | integer | `5` | Maximum number of fault-triggered in-place engine restarts (ADR-127) permitted within a rolling engine-restart-window-ms window before the instance escalates to a terminal shutdown (mirrors Kafka Streams bounding REPLACE_THREAD). Only error-motivated (abort) restarts consume this budget; programmatic / HA-demote graceful restarts do not. Set to 0 to disable in-place restart recovery (every fatal processing/production fault shuts the instance down). |
| `stoatflow.commit-barrier.engine-restart-window-ms` | integer | `300000` | Rolling window in milliseconds over which max-engine-restarts fault-triggered engine restarts are counted (ADR-127). A recurring/deterministic fault crashing every epoch is bounded to max-engine-restarts restarts within this window, then the instance shuts down rather than looping. |
| `stoatflow.commit-barrier.max-poison-replays` | integer | `10` | Maximum number of poison-epoch replays (ADR-140) permitted within a rolling poison-replay-window-ms window before the instance escalates to a terminal shutdown. A replay is what makes an asynchronous broker-side production failure non-destructive: the source offsets are held, the engine restarts in place, and the epoch reprocesses with the poison record skipped. Each replay costs a full engine restart, so this bounds a poison that does not converge (classically an oversized value derived from accumulated state). Separate from max-engine-restarts. Set to 0 to disable replay entirely. |
| `stoatflow.commit-barrier.poison-replay-window-ms` | integer | `60000` | Rolling window in milliseconds over which max-poison-replays is counted (ADR-140). In-memory only by design: exhausting the budget ends the process, Kubernetes restarts the pod and the budget returns clean, so CONTINUE is bounded per process rather than end to end. Alert on stoatflow.dlq.poison.replays.total. |
| `stoatflow.state.dir` | string | `${java.io.tmpdir}/stoatflow` | Directory for state store data. Should be on fast local storage (SSD recommended). |
| `stoatflow.state.uncommitted-max-bytes` | integer | `268435456` | Maximum total uncommitted bytes across all state stores, the timer store included, on every timer backend (global limit). Under exactly-once it also counts the output held back while a commit runs (the stoatflow.eos.send.buffer.bytes gauge), so a store-less topology is bounded too. When exceeded, triggers early commit barrier. Part of KIP-892 transactional semantics. Kafka Streams alias: statestore.uncommitted.max.bytes (its -1, disable, is refused). |
| `stoatflow.state.interactive-query-isolation-level` | enum | `READ_UNCOMMITTED` | Isolation level for interactive-query reads (store()), every store included. READ_UNCOMMITTED (default) sees writes buffered since the last commit barrier; READ_COMMITTED sees only state flushed by the last committed barrier, trailing processing by up to one barrier interval plus the commit. A store with no epoch buffer (lruMap, in-memory versioned) reads live with a WARN. Part of KIP-892; Kafka Streams key: default.interactive.query.isolation.level. One of: READ_UNCOMMITTED, READ_COMMITTED. |
| `stoatflow.state.restoration-enabled` | boolean | `true` | Whether state restoration from changelog topics is enabled. When enabled, automatically restores state on startup if local state is missing. |
| `stoatflow.state.restoration-pool-size` | integer |  | Restoration worker pool size. Each worker has its own Kafka consumer for parallel fetch throughput. Capped at min(poolSize, taskCount). Default: available processors × 2. |
| `stoatflow.state.restoration-validation-timeout-ms` | integer | `30000` | Bound (ms) on each store's startup validation, from that check's own start; at most `restoration-pool-size` checks run at once, the rest wait their turn without a bound. Each check reads a store's local RocksDB state once, read-only, without opening its data files — the MANIFEST, every live file's presence and size, and the stored offsets — and compares it with the store's changelog or source topic. A check still running at its bound — a RocksDB open stuck on a stalled disk — fails the start, naming the store, and is not waited for, so the pod restarts; a check's own failure fails the start at once. Every other startup probe of a store directory (the layout and format checks, the KTable source-switch check, the lock check before a deletion) gets the same bound, each on its own. Default: 30000 (30 s). |
| `stoatflow.state.restoration-metadata-timeout-ms` | integer | `30000` | How long the restore's startup metadata reads retry before the start fails: partition counts and end/begin offsets of every restore-relevant topic, and whether a KTable source topic is compacted (also on the HA standby). A read is retried every 500 ms while it fails or the topic is not visible yet; an authorization error fails at once. The reads behind the warning for a KTable switching from its source topic to a changelog — the consumer group's committed offsets among them — are tried once within this window, skipped once it has passed, and never fail the start. Also bounds the start-up output-topic check (validate-output-topics), the 5 s re-read of a topic answered missing included. Default: 30000 (30 s). |
| `stoatflow.state.restoration-batch-size` | integer | `20000` | Batch size for RocksDB writes during state restoration. Records are accumulated in a WriteBatch and flushed to RocksDB when this threshold is reached. Larger batches are more efficient but use more memory. |

| `stoatflow.state.sst-flush-interval-files` | integer | `10` | Number of SST file ingestions between offset flushes to disk. Lower values provide more frequent crash recovery points but add flush overhead. |
| `stoatflow.state.segment-checkpoint-records` | integer | `100000` | Segmented window/session store checkpoint cadence by record count (ADR-115 addendum). Segmented stores run WAL-off and become durable only on close(); a periodic checkpoint (flush dirty segments, then the offsets-holder) bounds the ungraceful-restart re-apply window. Invoked by the active commit path and the HA standby applier, whichever-first with segment-checkpoint-ms. Deliberately coarse (well below KS's ~10k-record flush) to limit SST/compaction churn. |
| `stoatflow.state.segment-checkpoint-ms` | integer | `30000` | Segmented window/session store checkpoint cadence by wall-clock milliseconds (whichever-first with segment-checkpoint-records). See segment-checkpoint-records. |

| `stoatflow.state.cleanup-delay-ms` | integer | `600000` | Delay in milliseconds before deleting RocksDB directories for state stores not declared in the current topology — including the timer-store once no processor declares timer types, and under the MEMORY timer backend, where it is a leftover of an on-disk backend (PERSISTENT or HYBRID). A stale timer-store may hold the only copy of its timers (WARN) unless the changelog and state restoration are on, no on-disk run without a changelog wrote the directory (it leaves a marker file there), and the timer changelog topic holds records — then the changelog holds them, and a MEMORY leftover's are restored (INFO). | `stoatflow.state.cleanup-dir-max-age-ms` | integer | `-1` | KIP-1259. Age threshold (ms) for purging local state store directories at startup. State dirs (per-store) untouched for at least this long are deleted and rebuilt from changelog (or source topic). Stores with no recovery source (logging disabled + no source topic; persistent timer store with changelog disabled) are never purged. Set >= the changelog's delete.retention.ms for the zombie protection to be meaningful. -1 (default) disables purging. Distinct from cleanup-delay-ms (orphaned-store cleanup). |
| `stoatflow.state.format-downgrade` | enum | `refuse` | What to do when a store's on-disk format is newer than the topology asks for — today, a headers-aware store (KIP-1271) opened with record headers turned off. refuse (default) fails startup with an actionable message and touches nothing on disk, so an accidental flag flip costs a restart rather than data. wipe-and-restore acknowledges the downgrade: the affected store's local state is deleted and rebuilt from its changelog (one full restore, bounded by changelog size). Two cases never reach this setting — an empty headers keyspace (the flag was flipped on and off with nothing written) is dropped in place for free, and a store with no recovery source (withLoggingDisabled(), or the global changelog disabled) is refused unconditionally. A downgrade sheds persisted headers from the local store. Re-enabling headers later upgrades lazily — the legacy values convert back with EMPTY headers — so the shed headers do not come back without a forced full restore. One of: refuse, wipe-and-restore. |
| `stoatflow.state.layout-mismatch` | enum | `refuse` | ADR-141, ADR-150. What to do when a RocksDB store's on-disk LAYOUT no longer describes what this build and topology ask for — every RocksDB key-value, versioned, timer, window and session store a built-in builder creates is checked at startup: a changed window size, a plain/timestamped value-format flip, a store-kind change, a retainDuplicates flip, a changed segment interval on a hand-built non-segmented store (where the segment id is baked into every key), or a local format version a newer or older StoatFlow wrote. Each of those would be misread rather than fail, producing confident wrong answers. A store that CAN be rebuilt is always rebuilt automatically: its local state is deleted and restored from its changelog or source topic, and this setting is not consulted. A value-format flip, a store-type change, a window-size change or a retainDuplicates flip on a store whose changelog is its recovery source cannot be rebuilt from it — the changelog holds the old layout (a window changelog's keys carry the window start only) — so it refuses whatever this says, leaving the store untouched: put the previous setting back, use a new store name, or reset the application (KSC-150). A stream-stream join's buffers are read by record timestamp, so a JoinWindows change is adopted in place. It applies only to a store with NO recovery source (withLoggingDisabled() or the global changelog disabled, and no source topic to restore from), where the local copy is the only copy — and there it also covers a rollback: a store whose local format or layout-stamp schema a newer StoatFlow wrote. refuse (default) fails startup naming every affected store, what moved and both values, and touches nothing on disk. wipe-and-restore accepts that the data is expendable and starts those stores EMPTY — for a store with no changelog this is permanent loss. A store that holds data a newer StoatFlow wrote and that this build cannot read — a newer layout-stamp schema on a store with a recovery source, or changelog records in a newer format — always refuses, whatever this says: run a build that reads it (roll forward). Distinct from format-downgrade, which governs a KIP-1271 record-headers downgrade; the two answer different questions. One of: refuse, wipe-and-restore. |
| `stoatflow.state.versioned.sweep-period-ms` | integer | `900000` | Target wall-clock time for one complete pass over a versioned store — the reclamation SLA, not the read SLA. A longer period costs less read bandwidth and leaves expired versions on disk longer. If the derived per-barrier slice exceeds max-scan-bytes-per-barrier the period is not achievable at that store size. |
| `stoatflow.state.versioned.max-scan-bytes-per-barrier` | integer | `8388608` | Primary cap: bytes read per barrier per sub-topology. The axis a sweep's cost is actually on — it reads and decompresses whole values to check an 8-byte key suffix, so on a large-value store the amplification against the bytes it needs is severe. Raise it when stoatflow.store.versioned.sweep.budget.exhausted.total climbs steadily. Must be at least 65536 (64 KiB): the sweep floors each store's derived slice there, so a smaller lane budget is an arithmetic contradiction rather than a throttle, and is rejected at start-up. |
| `stoatflow.state.versioned.max-scan-entries-per-barrier` | integer | `50000` | Secondary cap, for values small enough that per-entry CPU dominates instead of bytes. |
| `stoatflow.state.versioned.max-deletions-per-barrier` | integer | `10000` | Caps reclamation deletes added to one transaction. These ride the store's ordinary epoch batch, so they count toward uncommitted-max-bytes; at the default that is roughly 500 KB per tick against a 256 MB cap. Raising it substantially can start tripping MEMORY_PRESSURE barriers. |
| `stoatflow.changelog.enabled` | boolean | `true` | Whether changelog topics are enabled for state store backup. When enabled, all state mutations are written to Kafka as part of the transaction. |

| `stoatflow.changelog.num-partitions` | integer | `3` | Number of partitions for changelog topics. A changelog's partition count sets its write-throughput ceiling and decides how the store's data and write load shard across brokers - one partition funnels every write for that store through a single broker leader. Unlike Kafka Streams, where co-partitioning forces this to equal the source topic's partition count, StoatFlow's is decoupled and is therefore a real decision. Faster cold-start restore is a secondary, sub-linear effect. The cost is paid on every commit, because changelog records ride the same Kafka transaction as sink records. Prefer small counts and raise a specific store only on a measurement, using Materialized.withChangelogNumPartitions(n) and its siblings - which also let a small store be pinned back down to 1. | `stoatflow.changelog.reconcile-topic-configs` | boolean | `true` | ADR-142. Reconcile an ALREADY-EXISTING changelog topic's cleanup.policy and retention.ms against what its store asks for, on every start. Per-store topic configs used to be applied at creation only, so a changelog created by an older StoatFlow, by the migration tool (which creates every store's changelog compact / retention.ms=-1), or under a different retention kept those settings forever and never shed anything. Only those two keys are touched, and only for window and session stores: a plain key-value store's changelog is left alone, and so is a versioned store's, because in both cases a key's last value must survive regardless of age (ADR-142 section 5b). retention.ms is only ever WIDENED - a larger value you set yourself is kept and the decision logged, because the diff compares against the broker and cannot tell your value from ours, and narrowing a compact,delete topic makes the broker drop segments. | `stoatflow.processing-exception-handler` | string |  | Fully qualified class name for processing exception handler. Determines behavior when processor.process() throws an exception. |
| `stoatflow.rocks-db-config-setter` | string |  | Fully qualified class name of your own RocksDB options setter: a class with a public no-arg constructor implementing io.stoatflow.core.state.rocksdb.RocksDBConfigSetter, whose configure(storeName, RocksDbOptions) runs at every store open with the options the preset (rocks-db.preset) populated. Default: none (every store opens with the preset's options). The options a setter leaves are checked at every store open: with the write-ahead log off (write.disableWal = true, the default), db.atomicFlush = false logs a WARN naming the store (its changelog offsets could become durable ahead of its data), and write.sync = true refuses the open (RocksDB rejects synced writes without a WAL). |

| `stoatflow.processing-guarantee` | enum | `EXACTLY_ONCE` | Processing guarantee (ADR-092). AT_LEAST_ONCE: uses non-transactional producer with consumer.commitSync() for lower commit latency (no transaction, which costs ~8-30ms per commit); a commit flushes the epoch's output before its changelog records. Duplicate output possible on crash recovery. One of: EXACTLY_ONCE, AT_LEAST_ONCE. |

| `stoatflow.ha.pod-id` | string |  | Stable per-pod identity used as the metadata-topic record key and in diagnostics. Defaults to the POD_NAME env var (K8s downward API), else HOSTNAME, else the local hostname. |
| `stoatflow.ha.coordination-topic` | string |  | Metadata (coordination) topic name. Defaults to __stoatflow_<applicationId>_ha (single partition, compacted, auto-created). Must be exclusive to this application and single-partition (the at-least-once lease relies on the topic's total order); if overridden, never share it across applications. If the cluster denies auto-creation, StoatFlow logs the required spec at ERROR and fails startup. A pre-existing topic whose partition count is not 1 is reported at WARN and tolerated: reads and writes are both pinned to partition 0, so the extra partitions are unused. |
| `stoatflow.ha.heartbeat-ms` | integer | `1000` | Metadata-topic publish cadence (also the ALO lease republish cadence). |
| `stoatflow.ha.staleness-threshold-ms` | integer | `5000` | A peer is considered potentially down after this gap without a metadata-topic heartbeat. Pure downtime knob — correctness is guaranteed by the fence, not this threshold. Must be >= heartbeat-ms. |
| `stoatflow.ha.staleness-misses` | integer | `3` | Promote only after this many consecutive missed-heartbeat checks (debounce against transient jitter). |
| `stoatflow.ha.acceptable-recovery-lag` | integer | `50000` | Total committed-changelog lag (in records, summed across ALL changelog partitions — both RocksDB-store changelogs and StandbyReplicable caches) at or below which a standby is considered caught up: it publishes READY_STANDBY and is eligible to promote without the grace fallback. Default 50000 — this is a single total sum, NOT per-task like Kafka Streams' acceptable.recovery.lag (10000), so the KS number would be far too strict and ~one large epoch can approach it. Correctness never depends on it (restore-before-process does); mostly a raise-me lever. |
| `stoatflow.ha.promotion-grace-ms` | integer | `5000` | When the active is gone and no standby is within acceptable-recovery-lag, the least-behind standby auto-promotes after this bounded grace window (availability-first). Eligibility is re-checked continuously during the window. Defaults to approximately staleness-threshold-ms. |
| `stoatflow.ha.promotion-restore-no-progress-timeout-ms` | integer | `60000` | Progress-aware deadline for restore-before-process (bringing local state to the committed changelog end before processing): fails only if a full window of this length elapses with zero records applied (genuinely stuck), NOT the commit-path barrier timeout. On expiry the pod self-terminates and K8s restarts it (the fence already prevents split-brain). |
| `stoatflow.ha.promotion-settle-window-ms` | integer | `500` | Pre-fence election-token settle window (multi-standby N>2 leader election). After the elected winner claims the promotion token, it watches the compacted metadata topic for this long and only reaches the fence (EOS initTransactions / ALO producer wiring) if no competing claim (a higher epoch, or an earlier-offset same-epoch claim) becomes visible — so a competitor observes the winner before either fences (the F7 single-promoter guarantee). Must be in 1..staleness-threshold-ms; default 500 (about heartbeat-ms/2), above the worst-case claim propagation and below promotion-grace-ms. Returns immediately on a visible competitor; only the uncontended path pays the full window. |
| `stoatflow.ha.desired-standbys` | integer | `1` | Desired number of passive standbys (multi-standby N>2 election). Default 1 = today's N=2 pair (one active + one standby). K standbys survive concurrent failures at K-times changelog fan-out (redundancy, not scale). Drives the readiness redundancy floor (an active reports 'redundancy below desired' when it has fewer than this many caught-up standby spares) and the ha.redundancy.ready-standbys / ha.redundancy.below-desired metrics. Must be in 0..max-standbys. |
| `stoatflow.ha.max-standbys` | integer | `3` | Hard ceiling on the number of standbys, bounding K-times changelog fan-out (each standby runs its own continuous changelog reader = K-times broker read + K-times local storage). Default 3 = K <= 4 total. Cascaded/shared replication is future-scoped; this cap is the trigger to revisit. |
| `stoatflow.ha.failover-priority` | integer | `0` | Per-pod failover-placement hint (multi-standby election). Published on the heartbeat and used to order candidates WITHIN the equal-lag bucket (higher = preferred, e.g. a designated failover pod or a preferred zone). Never overrides lag (the election is lag-primary) nor the skew-invariant hash floor — it only breaks equal-lag ties. Default 0 (neutral). |
